## Compact Rules

Pre-digested rules per skill. Delegators copy matching blocks into sub-agent prompts as `## Project Standards (auto-resolved)`.

### branch-pr
- Every PR MUST link an approved GitHub issue — no exceptions.
- Every PR MUST carry exactly one `type:*` label.
- Automated checks must pass before merge; blank PRs without issue linkage get blocked by CI.
- Use the PR body sections: linked issue, PR type, summary, changes table, test plan, contributor checklist.
- No `Co-Authored-By` trailers in the PR body; conventional commit format.

### chained-pr
- MUST split when a PR exceeds 400 changed lines (additions + deletions), unless it has maintainer-approved `size:exception`.
- Design each PR for ≤60-minute human review; one deliverable work unit per PR.
- Every chained PR states where it starts/ends, what came before, what comes next, and is independently understandable/verifiable.
- Include a dependency diagram marking the current PR; if using Feature Branch Chain, open a draft tracker PR listing every child PR and its status.
- Once a chain strategy is picked, don't mix stacked and feature-branch patterns mid-chain.
- On SDD handoff, honor `delivery_strategy`: ask-on-risk, auto-chain, or require/record `size:exception`.

### work-unit-commits
- Commit by deliverable work unit (behavior/fix/migration/docs), never by file type (all models, then all services, then all tests).
- Keep tests in the same commit as the behavior they verify; keep docs with the feature/workflow they explain.
- A reviewer should understand why each commit exists from its diff + message alone.
- Each commit should be a candidate chained PR if the change grows.
- If SDD tasks forecast a >400-line change, group commits into chained-PR-ready slices before implementation.

### code-review
- ALWAYS read CLAUDE.md first (project root) — it defines conventions, forbidden patterns, and WHY behind non-obvious decisions.
- ALWAYS scan `docs/implementations/*.md` if present — explains motivation behind non-obvious changes (this repo doesn't have that folder yet; treat `openspec/changes/*/proposal.md` as the equivalent source of "why").
- Never approve if CRITICAL findings exist — escalate to the user instead.
- Never post a review to GitHub without explicit user confirmation first.
- Context beats convention: if CLAUDE.md/specs explain an odd-looking pattern, trust the docs, don't flag it as a bug.

### comment-writer
- Start with the actionable point — don't recap the whole PR before giving feedback.
- Warm and direct, like a thoughtful teammate, not a corporate bot; 1–3 short paragraphs or a tight bullet list.
- Always explain the technical *why* when requesting a change.
- Comment on the highest-value issue, not every minor preference (avoid pile-ons).
- Match the thread's language — if Spanish, use Rioplatense voseo (`podés`, `tenés`, `fijate`, `dale`).
- No em dashes — use commas, periods, or parentheses instead.

### issue-creation
- Blank issues are disabled — must use the bug-report or feature-request template.
- Every new issue gets `status:needs-review` automatically; a maintainer must add `status:approved` before any PR can open against it.
- Questions go to GitHub Discussions, not issues.

### cognitive-doc-design
- Lead with the decision/action/outcome; context comes after, not before.
- Progressive disclosure: happy path first, then edge cases and references.
- Chunk related info into small sections; keep flat lists short.
- Signpost with headings, labels, callouts, summaries.
- Prefer tables/checklists/examples over prose the reader must memorize.
- For PR/review docs: state what to review first, what's intentionally out of scope, and link chained PRs.

### judgment-day
- Before launching judges, resolve the skill registry and inject matching compact rules into BOTH judge prompts and the fix-agent prompt (identical for all).
- Launch exactly TWO blind, independent review sub-agents in parallel — never sequential, never do the review yourself as orchestrator.
- Neither judge agent knows about the other; both use identical criteria but may surface different issues.
- Confirmed real WARNINGs: fix inline, don't re-launch judges. Theoretical WARNINGs: report as INFO, don't fix/re-judge. Trivial SUGGESTIONs: fix inline, don't re-judge.
- Escalate after 2 iterations if judges still disagree.

### skill-creator
- Create a skill only when a pattern repeats, conventions diverge from generic best practice, or a workflow needs step-by-step/decision-tree guidance — not for trivial or one-off tasks.
- Start SKILL.md with the most critical patterns; use tables for decision trees; keep code examples minimal.
- Frontmatter `description` must include an explicit "Trigger:" clause — this registry and the skill-resolver protocol depend on it.

### dotnet-teacher
- Lead every explanation with the WHY before showing code; root-cause-first for "why does this fail" questions.
- Use Node/TS analogies only when they genuinely clarify (Task<T> ≈ Promise<T>, DI container ≈ NestJS providers, etc.).
- Give a pros/cons table at every real decision point, followed by a direct, context-aware recommendation — never bare "it depends."
- Flag anti-patterns immediately: `new HttpClient()`, `.Result`/`.Wait()` in ASP.NET, Scoped-into-Singleton injection, secrets in `appsettings.json`, blocking async in a loop, missing rate limiter/timeout, `AddDbContext` under high traffic instead of `AddDbContextPool`.
- Default LINQ guidance: `AsNoTracking()` for reads, filter (`Where`) before project (`Select`), project only needed columns, avoid premature `ToList()`.

### daily-update-clickup
- Never use markdown syntax (`*bold*`, `_italic_`) or `@[ID]`/`@Name` text mentions via the API — always build a Quill Delta array with `"text"` + `"attributes"` objects.
- Use the `"comment"` field (Quill delta), never `"comment_text"` (no rich text support).
- Mentions always go at the very end of the comment, after the "Posted via Claude standup skill" line; reference teammates by name in the body for readability.

### sync-to-notion
- Gather context from git diff/recent changes before writing; classify into bug fixes, features, refactors, security, observability, infra.
- Each item: Problem (1–2 sentences), Fix (1–2 sentences), Files touched.
- Check for an existing summary page before creating a duplicate; also save the summary locally.
