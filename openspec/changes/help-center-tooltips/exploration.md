# Exploration: `help-center-tooltips` — frontend integration for the Help Center

## Summary

The plan's §6 frontend contract (`HouseCenter.Api/docs/help-center-plan.md`) is **directionally correct on the API/data layer** (unversioned `/help/topics`, TanStack Query v5 hooks, query-key-per-session caching) but was drafted against **stale project documentation**. `housecenter-web`'s own `CLAUDE.md` and its three skills (`add-feature-slice`, `add-api-call`, `review-conventions`) describe an **Untitled UI + React Aria Components + Tailwind** architecture (`@/components/base/*`, `onPress`) that was **abandoned mid-project and migrated to MUI v9** — a deviation documented in the `housecenter-web` change's own `proposal.md` Status line but never backported into the docs or skills that generate new code. Every real reference page (`PatientsPage.tsx`, `ClinicsPage.tsx`, `Sidebar.tsx`, `NotificationBell.tsx`) uses plain `@mui/material` components with `onClick`. The plan's §6 text (written with awareness of "MUI v9 per its implemented deviations") already got this right for the `HelpTooltip` design — the risk is that a downstream `sdd-apply` phase, if it trusts the skill registry's cached rules instead of real code, will generate non-compiling or inconsistent output.

Beyond the UI-kit correction, one concrete gap the plan didn't anticipate: `Sidebar.tsx` does **not** render nav items generically from `NAV_ITEMS.roles` — it buckets them through hardcoded path arrays (`CORE_PATHS`/`REPORT_PATH`/`ADMIN_PATHS`) and a separate hardcoded icon lookup (`NAV_ICONS`). Adding a Help nav entry is a 3-file-touch, not a 1-line `NAV_ITEMS` push.

## Discrepancies / corrections vs. the plan's §6 sketch

1. **UI kit assumption source was fragile.** The plan's §6 prose already says "MUI" in a couple of places (`IconButton ... MUI`, "MUI Tooltip supports this") — that part is *correct*, but it's not clearly grounded; a downstream reader (or `sdd-apply`, or the auto-injected skill-registry rules from `add-feature-slice`/`review-conventions`) could easily default to the *documented* convention (`@/components/base/*`, `onPress`) since that's what those skill files literally say. **Action for `sdd-propose`/`sdd-tasks`: explicitly instruct implementers to follow `PatientsPage.tsx`/`ClinicsPage.tsx`/`PageHeader.tsx` as ground truth, and flag `housecenter-web/CLAUDE.md` + its three skills as stale on the UI-kit dimension only** (everything else in those docs — four-layer pattern, `@/` alias, named exports, query-key factory, RBAC guards, no test runner — is still accurate and confirmed above).
2. **Sidebar wiring is under-specified in the plan.** Plan says "Add a 'Help' entry to the sidebar nav (`/help`, `roles: ALL_ROLES`)" as if one `NAV_ITEMS` push suffices. In reality `Sidebar.tsx` requires **three** coordinated edits:
   - `src/lib/constants.ts:22-32` — add the `NAV_ITEMS` entry (as planned).
   - `src/components/shared/Sidebar.tsx:46-48` — add `/help` to one of `CORE_PATHS`/`REPORT_PATH`/`ADMIN_PATHS` (or introduce a new bucket) — items not in any bucket array **silently don't render**, regardless of `NAV_ITEMS`/role filtering.
   - `src/components/shared/Sidebar.tsx:33-44` — add a `help` key to `NAV_ICONS` mapped to a real `@mui/icons-material` component (e.g. `HelpOutlineOutlined`) — this is a *separate* lookup from `Icon.tsx`'s `paths` map, and `Icon.tsx` is not the live icon system (see Confirmed above), so the plan's implicit assumption of touching `Icon.tsx`'s `paths` map for a nav icon is the wrong file entirely.
3. **`Icon.tsx`'s `paths` map is not the right place for a help/info icon** at all, for the same reason: it's nearly-dead legacy code (1 consumer). Use `@mui/icons-material`'s `HelpOutlineOutlined` (or `InfoOutlined`) directly in `HelpTooltip`, consistent with every other icon in the app.
4. **Froala/rich-text infrastructure already exists** (`froala-editor`, `react-froala-wysiwyg` deps; `src/components/shared/RichTextEditor.tsx`/`RichTextView.tsx`, actively used in `TreatmentsTab.tsx`, `CommentsTab.tsx`, `ConsultationDetailPage.tsx`). This directly **contradicts** the backend plan's Open Question #1 framing ("Rich text (HTML) would reopen the legacy Froala mistake the housecenter-web proposal explicitly walked away from") — Froala was in fact reintroduced for other modules. This does not make reusing `RichTextView` cheaper than adding a markdown renderer, though, because the backend content is **already seeded as real Markdown syntax** (`##` headings etc., see Confirmed above) — switching to Froala/HTML rendering now would require re-authoring all seeded content. **Recommendation stands with the plan: add a markdown renderer**, but flag `markdown-to-jsx` as a lighter single-dependency alternative to `react-markdown` worth a pick in `sdd-propose` (smaller bundle, no remark/rehype ESM toolchain, safe-by-default no raw HTML passthrough) given this is a low-traffic, content-simple use case.
5. **Minor path-naming correction**: the base API client lives at `src/api/client.ts`, not `src/api/apiClient.ts`.

## Additional considerations for the proposal — feature-slice shape question

This change does **not** cleanly fit the `add-feature-slice` skill's assumed shape, and should be scoped as two distinct workstreams in `sdd-propose`/`sdd-tasks`:

- **Workstream A — conventional read-only slice** (`help.types.ts` → `help.api.ts` → `useHelpTopics`/`useHelpTopic` → `HelpIndexPage`/`HelpTopicPage` + route + nav). This *does* fit the four-layer convention, just without the create/update/delete mutation half that `add-feature-slice` assumes by default (admin authoring UI is explicitly deferred per the backend plan). Scaffold this the normal way, skipping the mutation-hook/form-schema steps.
- **Workstream B — cross-cutting integration**, which is genuinely different in shape from any existing slice: a shared `HelpTooltip` component consumed from `PageHeader` (1 additive prop) plus surgical single-line insertions into ~7-10 *already-existing, unrelated* pages/dialogs (`SessionsTab.tsx` status dialog, `TreatmentsTab.tsx` status dialog, `ConsultationDetailPage.tsx` status dialog, `WorkRoutesPage.tsx`/destination editor, `InvitationsPage.tsx`, `UsersPage.tsx` roles dialog, patient assign-doctor/assign-collaborator forms). No existing skill or slice precedent covers "one small component wired into many unrelated files." For the **Review Workload Guard**: total changed lines will likely be small (each insertion is 1-3 lines), but the **file-count spread is wide** (10+ files across 5+ feature areas) — this is a different risk shape than the usual "too many lines in one file" forecast, and `sdd-tasks` should call it out explicitly as a fan-out risk, recommending the same phased/chained approach the backend used (Workstream A as one PR/slice, Workstream B split by feature area — e.g. sessions+treatments+consultations anchors together, admin-management anchors separately — rather than one PR touching everything).
- Also worth deciding explicitly in `sdd-propose`: whether `NAV_ITEMS`/`Sidebar.tsx` gets `/help` bucketed into `CORE_PATHS` (visible to everyone, top of list) or its own new group — given `ALL_ROLES` includes Sponsor, `CORE_PATHS` is the more consistent choice (matches Patients/Clinics/Work Routes/Reports placement).

## Recommendation

Proceed to `sdd-propose` with the plan's §6 contract as the base, applying the corrections above. Concretely:
1. Keep TanStack Query hooks, unversioned `/help` API base, and role list exactly as planned — these were validated against real code and require no change.
2. Build `HelpTooltip` on MUI `Tooltip` + `IconButton` + `HelpOutlineOutlined`, per `PatientsPage.tsx`/`ClinicsPage.tsx`/`NotificationBell.tsx` conventions — not per `housecenter-web/CLAUDE.md`'s stale Untitled-UI/React-Aria description.
3. Treat the Sidebar/`NAV_ITEMS` wiring as a 3-file task (`constants.ts` + `Sidebar.tsx` bucket array + `Sidebar.tsx` `NAV_ICONS`), not a 1-line change.
4. Pick a markdown renderer in `sdd-propose` (recommend evaluating `markdown-to-jsx` as a lighter alternative to `react-markdown`) — confirmed necessary since backend content is real Markdown.
5. Split `sdd-tasks` into the two workstreams described above, with Workstream B chunked by feature area to control review fan-out.
6. Flag to whoever runs `sdd-apply`: do not trust `housecenter-web`'s own skill-registry-cached rules for the UI-kit dimension; verify against `PatientsPage.tsx`/`ClinicsPage.tsx`/`PageHeader.tsx` first.

## Risks

- **Stale project skills risk regressions.** If `sdd-apply`'s injected "Project Standards (auto-resolved)" block is sourced from `housecenter-web`'s skill registry without this correction, generated code will reference a nonexistent `@/components/base/*` and use `onPress`, producing a build failure. The orchestrator should re-resolve/patch the cached compact rules for `housecenter-web` before the apply phase, or pass this exploration's correction inline.
- **Sidebar fan-out is easy to under-scope** (see Discrepancy #2) — a naive "just push to NAV_ITEMS" task will ship a Help entry that's invisible in the sidebar.
- **Cross-cutting file-spread review risk** (Workstream B) — wide file-touch surface even at low line-count; needs explicit chaining, not just line-count-based sizing.
- **Markdown dependency choice is still open** — needs a decision in `sdd-propose` (react-markdown vs markdown-to-jsx), not blocking but should not be deferred silently into `sdd-apply`.
- **Minor inaccuracies already present in this session's own `state.yaml`** (React 18 vs actual React 19; `@/components/base/*`/`onPress` restated as fact) should be corrected when `sdd-propose` runs, so they don't propagate further.

## Ready for Proposal

Yes. No blocking unknowns remain — the two items intentionally left open (markdown library pick, exact Sidebar bucket placement) are proposal-level decisions, not exploration gaps.
